The problem

You update a record. The old value is gone.

So teams bolt history on — and end up running two systems, one for the present and one for the past.

History tables & triggers

Hand-rolled, row by row

Every table gets a shadow table. Querying "as of" means joins over validity columns you maintain yourself.

Event sourcing

The past means replay

The log is complete, but reading yesterday's state means rebuilding it from the beginning or maintaining projections.

Warehouse time travel

Know your retention policy

Warehouse recovery windows are limited. Lakehouse history lasts until cleanup removes old snapshots, logs or data files; retention is configurable and defaults vary.

Iceberg maintenance · Delta retention

Retention limits: Snowflake, BigQuery, Databricks Delta.

What makes Sirix different

History is the data model, not a feature.

Six properties that, together, no other open-source database offers. Each one is a direct consequence of how Sirix stores revisions: immutably, and sharing everything that did not change.

01 · Time travel

Any revision reads like the latest.

Open the past by revision number or timestamp, and query it with the full language — directly, not by replaying a log.

Every commit is an immutable revision with its own root. Opening one is O(1) by number and O(log R) by timestamp; each page read combines at most N fragments, where N is a configurable window, so revision 1 costs the same as revision 10,000.

JSONiqtime travel
(: the catalog exactly as it was at revision 1 :)
jn:doc('shop','products', 1)

(: or as it was at 3 a.m. last Tuesday :)
jn:open('shop','products', xs:dateTime('2026-11-10T03:00:00Z'))

Source: README · Page Versioning Strategies, BENCHMARKS.md · Benchmark 2

02 · Complete history

Keep everything. Pay only for what changed.

A new revision shares every unchanged page with the one before. By default it writes only the changed records, plus their path to the root.

Versioning goes below the page: a commit writes a page fragment for each changed data page. Because the page tree is copy-on-write, it also writes new copies of the small index pages on the path from each changed leaf up to a new revision root — a handful of pages, logarithmic in the data size.

What a fragment holds is a per-resource choice of versioning type, trading write cost against read cost:

Versioning types and what each writes per changed page
TypeA changed page writesFragments per read
Sliding snapshot defaultthe changed records, plus any record about to fall out of the N-fragment window (N configurable per resource)≤ N
Incrementalthe changed records; a full page every N revisions≤ N
Differentialevery record changed since the last full page2
Fullthe whole page1

With the default, storage per revision follows the change, not the document, and reads stay bounded without the write spikes of periodic full snapshots.

Don't need everything forever? SirixDB Enterprise adds retention policies — keep the last N revisions, everything newer than a date, or a chosen set — and compaction that physically reclaims the space (in development).

Javaconfigure per resource
ResourceConfiguration.newBuilder("orders")
    .versioningApproach(VersioningType.SLIDING_SNAPSHOT) // default
    .build();

Source: README · The Solution, Page Versioning Strategies, WHY-SIRIX §3

03 · Node-level identity

Every field has an identity. Every diff is exact.

Each JSON object, array, field and value keeps a stable key across revisions, so Sirix can tell you exactly which nodes changed.

Diffs compare trees, not text: the result is a list of node-level inserts, updates and deletes. With hashes enabled, unchanged subtrees are skipped. The same identity lets you follow one field through its whole history with jn:all-times, jn:previous and jn:next.

RESTdiff two revisions
curl "localhost:9443/shop/products/diff?first-revision=1&second-revision=4"

Source: README · Diff, OpenAPI · Diff schema, WHY-SIRIX §2

04 · Native valid time

What did you know — and when was it true?

Two time axes: transaction time (when Sirix recorded it, every commit) and valid time (when it was true in the world, from your documents).

Alice moves from Berlin to Munich on Mar 1, but only tells you on Mar 10. You record the move on Mar 10, effective Mar 1. Ask what your records said on Mar 5 and Sirix answers Berlin — that is what you knew when you mailed her invoice. Ask today and it answers Munich for Mar 5, and still Berlin for Feb 20.

JSONiqboth axes at once
(: recorded Mar 5, valid Mar 5 → Berlin :)
jn:open-bitemporal('crm','customers',
  xs:dateTime('2026-03-05T00:00:00Z'),  (: transaction time :)
  xs:dateTime('2026-03-05T00:00:00Z'))  (: valid time       :)
(: recorded today, valid Mar 5  → Munich :)
(: recorded today, valid Feb 20 → Berlin :)

Valid time is two fields you name per resource (validFrom/validTo), indexed by a versioned interval index. Recording the move is one ordinary commit: it ends the Berlin record at Mar 1 and adds Munich from Mar 1. Sirix has no FOR PORTION OF-style automatic split yet.

Source: README · Bitemporal, Bitemporal Queries (half-open validity in jn:open-bitemporal)

05 · Embeddable, with analytics built in

A library first. A server when you want one.

Add one dependency and you have a versioned database in a directory — or run the same engine as a REST server, CLI, MCP server for AI agents, or GraalVM native binary.

Every index is versioned too: path, value (CAS), name, valid-time and columnar projection indexes all open "as of" any revision. Projection indexes feed SIMD kernels for group-bys and aggregates over a past state — and fall back to the regular pipeline whenever they can't answer exactly.

Gradleembed
implementation("io.sirix:sirix-core:1.0.0-beta7")

06 · Immutable revisions · AI agents

Let AI agents edit real data — and undo them.

Every revision is immutable. An agent's edit is just a new revision you can inspect, diff and revert — and the bad state stays in history as evidence.

The built-in MCP server lets agents (Claude, Cursor or any MCP client) read any revision, inspect structural diffs and optionally revert. It is read-only by default, with access control, output sanitization and an audit log. A revert appends a new revision that restores the whole resource, guarded by the head you expect: if someone committed in between, it returns 409 and changes nothing.

Shellregister with your MCP client
# read-only by default
sirix-mcp --database-path /data/sirix
# allow edits (and reverts)
sirix-mcp --database-path /data/sirix --read-write

Source: README · MCP server, AGENT_QUICKSTART, QUICKSTART · revert

What you can do

Ask questions about the past in one line.

JSONiq with temporal functions, a REST API, and the same operations from Java or the CLI. Every example below uses functions documented in the Sirix README.

Read a resource as it was — over REST, or inside any query.

REST
curl 'localhost:9443/mydb/products?revision=1'
# -> [{"id":1,"name":"keyboard","price":49.9},{"id":2,"name":"mouse","price":19.9}]
JSONiq
count(jn:doc('mydb','products', 1)[])   (: -> 2 :)
count(jn:doc('mydb','products')[])      (: -> 3, the latest :)

Because each node keeps its identity, you can walk one field through every revision without touching the rest of the document.

JSONiq
for $v in jn:all-times(jn:doc('mydb','myresource').users[0])
return {"rev": sdb:revision($v), "data": $v}

Also: jn:previous, jn:next, jn:first, jn:last, jn:past, jn:future, plus sdb:timestamp and commit authors and messages.

A structured diff between any two revisions, from a query or over REST.

JSONiq
jn:diff('mydb','myresource', 1, 5)
REST · real output from the quickstart
curl 'localhost:9443/mydb/products/diff?first-revision=1&second-revision=2'
{"database":"mydb","resource":"products","old-revision":1,"new-revision":2,
 "diffs":[{"insert":{"nodeKey":10,"insertPositionNodeKey":6,
           "insertPosition":"asRightSibling","path":"/[2]","type":"jsonFragment"}}]}

Name the valid-time fields once per resource; the JSONiq and REST store layers create the interval index for you.

JSONiq
(: valid on July 15, per the latest knowledge :)
jn:valid-at('mydb','myresource', xs:dateTime('2024-07-15T12:00:00Z'))

(: known on Jan 20 AND valid on July 15 :)
jn:open-bitemporal('mydb','myresource',
    xs:dateTime('2024-01-20T10:00:00Z'),
    xs:dateTime('2024-07-15T12:00:00Z'))

Revert appends a new revision that restores an old state — the bad edit stays in history, inspectable. A stale expectedHead returns 409 and changes nothing, which makes it safe for agents.

REST
curl -X POST localhost:9443/mydb/products/revert \
  -H 'Content-Type: application/json' \
  -d '{"targetRevision":1,"expectedHead":2,"message":"Undo agent product edit"}'
# -> {"revision":3,"previousHead":2}

The MCP server exposes time-travel reads, structural diffs and revert to AI agents. It is read-only by default, with access control and an audit log.

Declare a columnar projection over a record set; plain JSONiq group-bys and aggregates route through it automatically, at any revision.

JSONiq · experimental
let $doc := jn:doc('mydb', 'sales.jn')
let $idx := jn:create-projection-index($doc, '/[]',
    ('/[]/age', '/[]/active', '/[]/dept', '/[]/city'),
    ('long', 'boolean', 'string', 'string'))
return {"revision": sdb:commit($doc)}

Open core

Embedded today. Retention and scale-out when you need them.

The open-source engine is single-node by design. SirixDB Enterprise, a commercial edition in development, adds what the comparison above says is missing, using storage providers that plug into the same engine and on-disk model.

  • Retention policies and compactionin developmentDecide how long history lives: keep the last N revisions, everything newer than a date, or a chosen set. Compaction then physically reclaims the space of pruned revisions; each keeps its number and timestamp as a tombstone, and opening it is refused.
  • Web consolein developmentA dashboard across your databases plus audit reports: a cross-resource activity timeline with author filtering, and compliance exports of the audit trail.
  • Object storage (S3 and compatibles)in developmentEach commit becomes an immutable segment object plus a small manifest, read through an in-memory page cache. Immutable revisions are a natural fit for object storage.
  • Read replicas over Kafkain developmentA leader publishes one small event per commit; followers reload the leader's manifest from shared storage and serve the same revisions. Still one writer per resource.

Getting started

From zero to time travel in three commands.

A disposable local server with authentication off, for evaluation on Linux x86-64. Production setup with OAuth2 is in the operations guide.

Start the server

Pinned image, loopback only, data removed on exit.

Shell
docker run --rm --name sirix-first-run -p 127.0.0.1:9443:9443 \
  -e SIRIX_AUTH_MODE=none \
  sirixdb/sirix@sha256:76cb3ec3f8c1efa2d62b526962ff5fed1f7b3f7436bb34db4685abc7320ad33a

Write revision 1

Any JSON document becomes a versioned resource.

Shell
curl -X PUT localhost:9443/first-run/message \
  -H 'Content-Type: application/json' \
  -d '{"message":"hello"}'

Change it, then go back

An update query commits revision 2; revision 1 stays readable.

Shell
curl -X POST localhost:9443/ \
  -H 'Content-Type: application/json' -d "{\"query\":\"replace json value of jn:doc('first-run','message').message with 'hi'\"}"
curl 'localhost:9443/first-run/message?revision=1'
# -> {"message":"hello"}

Embed it

io.sirix:sirix-core:1.0.0-beta7 on JDK 25. A runnable example commits two revisions and reads the first back.
